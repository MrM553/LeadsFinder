# CLAUDE.md — LeadFinder

Permanent development instructions for this project. Read this before making any change. Keep it updated whenever an architectural decision changes — out-of-date instructions are worse than none.

(See also `AGENTS.md`, generated by the Next.js scaffold, for generic Next.js agent conventions. This file is the authoritative source for LeadFinder-specific rules.)

## 1. Project Purpose

LeadFinder is a **lead research and lead management tool** for a German web agency (Handwerker, Steuerberater, and similar local-service businesses as target customers).

Pipeline: **FIND → ANALYZE → SCORE → STORE → REVIEW.**

The agency owner searches for a German industry + location (e.g. "Dachdecker Rosenheim"), the system finds ~100 candidate business websites, collects publicly available business information, analyzes each website against measurable criteria, computes a transparent 0–100 lead score, stores everything, and presents it in a dashboard for manual review.

**This is a research/CRM tool, not an outreach tool.** See §5 (hard boundary).

This is a standalone project. It does **not** modify, depend on, or share infrastructure/credentials with the agency's existing website (`../CompanyWebsite`). Never reach into that directory.

## 2. Architecture

```
Frontend (Next.js, TypeScript)
  └─ Dashboard: search, lead table, lead detail, notes, status
  └─ Calls internal API routes only — never calls external providers directly

API layer (Next.js route handlers / server actions)
  └─ Auth-gated
  └─ Orchestrates: search provider → website fetch → analysis → scoring → DB write
  └─ Holds all external API keys server-side only

Data layer
  └─ Relational DB (leads, searches, scoring_rules, notes)
  └─ Local dev: SQLite (via Drizzle) — mirrors Cloudflare D1 semantics
  └─ Production: Cloudflare D1

Background/async work (introduced only in Milestone 6, when needed)
  └─ Search jobs that take too long for a single request
  └─ Cloudflare Queues in production; simple in-process async locally
```

Principles:
- Server-side only for anything involving API keys, scraping, or scoring logic. The browser never talks to a search provider or fetches third-party websites directly.
- The analysis/scoring pipeline is a set of pure(ish), testable functions — not entangled with HTTP handlers — so scoring rules can be unit tested and later reused by a background job.
- Every external write (search API call, website fetch) is logged with enough context (source URL, timestamp) to explain where any stored fact came from.

## 3. Technology Decisions

| Layer | Choice | Why |
|---|---|---|
| Frontend framework | Next.js (App Router) + TypeScript | User's preference; maps cleanly to Cloudflare via OpenNext/Workers |
| Styling | Tailwind CSS + shadcn/ui | Fast to build a clean dashboard; no design system to invent |
| Data fetching (client) | React Query | Caching/refetching for dashboard tables without hand-rolled state |
| Database (local) | SQLite via Drizzle ORM | Zero setup, file-based, same schema shape as D1 |
| Database (production) | Cloudflare D1 | Compatible with Workers deployment; SQLite-compatible with Drizzle |
| ORM | Drizzle | Typed, lightweight, works with both SQLite and D1 without rewriting queries |
| Auth | Custom signed-cookie session (scrypt password hash + HMAC-signed session token, no external auth library) | Single agency-owner account, not multi-tenant; avoids NextAuth's provider/adapter surface for a need this small — see `src/server/auth/` |
| Deployment | Cloudflare Workers (via OpenNext for Next.js) | User requirement; investigate current recommended adapter at deploy time (Milestone 7) — don't lock this in prematurely |
| Package manager | npm (unless user states a preference) | Default; revisit if asked |
| Lead discovery | OpenStreetMap Overpass API (free, no key, no signup) for candidate businesses by category + location | Fully free; strong German POI coverage; returns structured name/address/phone/website tags that map directly onto lead fields; avoids Google Places API's data-caching/retention restrictions |

Do not introduce a new library, framework, or service without checking whether an existing dependency already solves the problem, and without noting the decision here.

## 4. Coding Conventions

- TypeScript everywhere, strict mode on. No `any` unless justified with a comment on *why*.
- Functional React components. No class components.
- Server-only code (API keys, DB access, scraping/fetching) lives under `src/server/` or in route handlers — never imported into client components.
- Environment variables accessed through a single typed `env.ts` validator (e.g. zod), not `process.env` scattered through the codebase.
- Filenames: kebab-case for files, PascalCase for React components, camelCase for functions/variables.
- No commented-out code, no speculative abstractions. Three similar lines beat a premature helper.
- Default to no code comments; add one only when the *why* isn't obvious from the code (a workaround, a non-obvious constraint).

## 5. Security Requirements

- **The dashboard requires authentication.** No unauthenticated route may read or write lead data. `src/proxy.ts` (Next.js 16's middleware convention) does a cheap cookie-presence redirect for page UX only — the real enforcement is `getSession()` (full HMAC + expiry verification) called at the top of every protected server component and API route (see `src/server/auth/`).
- All API keys (search provider, etc.) are server-side environment variables only. Never sent to or readable by the browser.
- Validate and sanitize all user input at API boundaries (zod schemas on every route handler).
- Parameterized queries only (Drizzle handles this) — no raw string-built SQL.
- Rate-limit API endpoints, especially the search/analysis endpoints, to avoid runaway cost or accidental abuse.
- Production secrets are never committed to Git. Use `.env.local` locally (gitignored) and Cloudflare secrets in production. `.env.example` documents required variable *names* only, never values.
- No functionality may automatically contact a business (email, SMS, WhatsApp, phone, LinkedIn, etc.) — see §8. This is a hard product boundary, not just a security concern.

## 6. Data & Privacy Principles

- Collect **business** information only: company name, business phone/email published by the business itself, website, address/city/region. Do not collect personal data about individuals (owners' personal emails, personal social profiles, etc.) beyond what a business publishes about itself in a business context.
- **Never fabricate or guess data.** If a phone/email/field isn't found on the site, leave it null — do not pattern-guess an email address (e.g. `info@domain.de` guessed without seeing it).
- Every collected fact should be traceable to a `source_url` and a `date_found` / `last_checked` timestamp.
- Store the minimum necessary. No scraping of unrelated pages "just in case."
- Under GDPR, published business contact details (Impressum-style B2B info) used for a legitimate B2B research purpose is generally lower-risk than personal data, but this is not legal advice — flag any ambiguous case to the user rather than deciding unilaterally.

## 7. Rules for Web Research / Scraping

- Respect `robots.txt` for every domain before fetching.
- Never bypass CAPTCHAs, logins, paywalls, or anti-bot mechanisms.
- Use the OpenStreetMap Overpass API for discovery (free, structured, no key required) rather than scraping search engine result pages directly. Query by OSM tags matching the target industry (e.g. `craft=roofer`) and location (bounding box / area matching the German city or region).
- Overpass data is under ODbL — internal CRM use is fine, but if any OSM-derived data is ever shown outside the tool (public page, exported report), OSM attribution is required.
- Reasonable request rate: throttle/delay between requests to the same domain; a small concurrency cap across domains.
- Set a real, identifiable User-Agent and reasonable timeouts; back off and give up gracefully on failure — don't retry aggressively.
- Cache fetched pages/results for a reasonable period (`last_checked`) instead of re-fetching on every view.
- This is not a crawler: fetch only the pages needed to assess a business (homepage, maybe one or two linked pages such as contact/impressum) — never a full-site crawl.
- Always persist the `source_url` for anything stored.

## 8. Hard Product Boundary — No Outreach

LeadFinder never sends a cold email, SMS, WhatsApp message, LinkedIn message, or phone call, and never schedules one automatically. It finds, analyzes, scores, stores, and displays leads for the agency owner to act on manually. Do not add outreach automation even if it seems like a natural next step — it requires an explicit, separate decision from the user, out of scope for this project as currently defined.

## 9. Database Conventions

- Migrations are checked into the repo (Drizzle migrations folder); never hand-edit the DB schema outside of a migration.
- Every table has `id`, `created_at`, `updated_at`.
- Lead deduplication key: normalized website domain (and/or normalized company name + city) — decide exact rule in Milestone 1 and document it here once fixed.
- Enum-like fields (lead status, website status, etc.) are defined once in a shared constants/types file and reused by both the DB schema and the UI — no duplicated string literals.
- Seed/test data lives in a separate seed script, clearly fake (no real scraped business data used as fixtures).

## 10. Testing Requirements

- Scoring logic and analysis heuristics (pure functions) must have unit tests — this is the most important logic to get right and keep transparent.
- API route handlers get at least a basic integration test (auth required, input validation, happy path).
- Do not chase 100% coverage; prioritize the scoring engine, dedup logic, and auth gates.
- Before marking a milestone done, run the test suite and confirm it's green.
- **Tests never touch the dev/seed database.** `vitest.setup.ts` forces `DATABASE_URL` to a separate `data/leadfinder.test.db`, wipes it, and re-applies migrations before each test file runs. This was a real bug caught during Milestone 6 (test-inserted fixtures were showing up in the dev dashboard) — if you ever see unfamiliar "Testberuf"/similar rows in dev data, check that setup file is still wired up.

## 11. Deployment Conventions

- Local development is the default and must always work without any Cloudflare account (SQLite, `.env.local`).
- Cloudflare deployment is introduced in Milestone 7, not before. Investigate the current recommended Next.js-on-Workers path at that time rather than assuming today's adapter is still current.
- Only introduce Cloudflare services (D1, R2, Queues, etc.) when there's a concrete need for them in the milestone being worked on — not preemptively.
- Production secrets are set via `wrangler secret` / Cloudflare dashboard, never committed.

## 12. Before Modifying Existing Code

Before changing any existing file: read it fully, understand why it's structured the way it is, and check for related files (types, tests, callers) that the change affects. Don't guess at intent from a filename. If a change touches the scoring engine or DB schema, check for existing tests/migrations first.

## 13. Do Not Implement Prematurely

Build only what the current milestone (see `MILESTONES.md`) requires. The following are explicitly deferred — design so they *could* be added later, but do not build them now:

AI website audits, website screenshots, additional search providers, CSV export, advanced CRM features, lead enrichment, personalized audit generation, outreach tracking, automated follow-up reminders, team accounts, multi-tenant/SaaS mode.

When in doubt about scope, ask rather than build ahead.
